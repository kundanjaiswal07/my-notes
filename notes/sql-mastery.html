What is SQL & Relational Databases
Basics⌄
📖 Explanation

SQL (Structured Query Language) is the standard language for communicating with relational databases. A relational database stores data in tables (rows and columns), with relationships between tables enforced by keys. SQL divides into four sublanguages: DDL (Data Definition — CREATE, ALTER, DROP), DML (Data Manipulation — SELECT, INSERT, UPDATE, DELETE), DCL (Data Control — GRANT, REVOKE), and TCL (Transaction Control — COMMIT, ROLLBACK).

Every table has a Primary Key — a unique identifier for each row. A Foreign Key links to a primary key in another table, creating the relationship. Popular databases include MySQL, PostgreSQL, SQL Server, Oracle, and SQLite — all use near-identical SQL with minor dialect differences.

Table — rows (records) × columns (attributes); each cell holds one value
Primary Key — unique, non-NULL identifier per row; one per table
Foreign Key — column that references a PK in another table; enforces referential integrity
DDL — CREATE, ALTER, DROP — defines structure
DML — SELECT, INSERT, UPDATE, DELETE — manipulates data
-- Create a table (DDL) CREATE TABLE employees ( emp_id INT PRIMARY KEY, name VARCHAR(100) NOT NULL, dept_id INT REFERENCES departments(dept_id), salary DECIMAL(10,2), hire_date DATE DEFAULT CURRENT_DATE ); -- Insert a row (DML) INSERT INTO employees (emp_id, name, dept_id, salary) VALUES (1, 'Alice', 10, 75000.00); -- Retrieve data (DML) SELECT * FROM employees;
Interview Questions
Q1. What is the difference between a Primary Key and a Foreign Key?Reveal
Answer: A Primary Key (PK) uniquely identifies each row in its own table — must be unique and NOT NULL. A Foreign Key (FK) is a column in one table that points to a PK in another table, creating a relationship between them. A PK enforces entity integrity; a FK enforces referential integrity (you can't insert an FK value that doesn't exist in the referenced table).
Q2. What are DDL, DML, DCL, and TCL?Reveal
Answer:
  • DDL (Data Definition Language): CREATE, ALTER, DROP, TRUNCATE — changes schema structure
  • DML (Data Manipulation Language): SELECT, INSERT, UPDATE, DELETE — works with data
  • DCL (Data Control Language): GRANT, REVOKE — manages permissions
  • TCL (Transaction Control Language): COMMIT, ROLLBACK, SAVEPOINT — manages transactions
DDL changes are auto-committed; DML changes require explicit COMMIT in a transaction.
Q3. What is referential integrity and how is it enforced?Reveal
Answer: Referential integrity ensures that a foreign key value always points to an existing primary key. Enforced by:
  • ON DELETE CASCADE — deleting parent row deletes child rows too
  • ON DELETE SET NULL — deleting parent sets child FK to NULL
  • ON DELETE RESTRICT (default) — prevents deletion if child rows exist
Without FK constraints, orphan rows accumulate silently.

SELECT & Column Basics
Basics⌄
📖 Explanation

SELECT is the most fundamental SQL command — it retrieves data from one or more tables. The basic structure is SELECT columns FROM table. SELECT * returns all columns but is inefficient in production — always name the columns you actually need. DISTINCT removes duplicate rows from the result. Column aliases (AS) rename columns in output without changing the table.

SQL executes in a specific logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. This matters because you cannot reference a SELECT alias in a WHERE clause (WHERE executes before SELECT).

SELECT col1, col2 — name columns explicitly; never SELECT * in production
SELECT DISTINCT — removes duplicate rows from result set
AS alias — rename column/table in output; quote if alias has spaces
Logical order — FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
-- Basic SELECT SELECT emp_id, name, salary FROM employees; -- All columns (avoid in production) SELECT * FROM employees; -- Aliases SELECT name AS employee_name, salary * 12 AS annual_salary, dept_id AS department FROM employees; -- DISTINCT — unique values only SELECT DISTINCT dept_id FROM employees; -- Expression in SELECT SELECT name, salary, salary * 0.1 AS bonus FROM employees;
Interview Questions
Q1. Why should you avoid SELECT * in production queries?Reveal
Answer: Three reasons: (1) Performance — fetches all columns including ones you don't need, wasting I/O and network transfer. (2) Brittleness — if a column is added or reordered, your application code may break or return unexpected data. (3) Index coverage — SELECT with named columns can be satisfied by a covering index; SELECT * forces a full table read. Always list the columns you need explicitly.
Q2. Can you use a SELECT alias in the WHERE clause? Why or why not?Reveal
Answer: No. SQL executes in logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. The WHERE clause is evaluated before SELECT, so aliases defined in SELECT don't exist yet when WHERE runs. Fix: wrap in a subquery or CTE: SELECT * FROM (SELECT salary*12 AS annual FROM employees) t WHERE annual > 600000.
Q3. What is the difference between DISTINCT and GROUP BY for deduplication?Reveal
Answer: SELECT DISTINCT col returns unique values of that column — simple deduplication. GROUP BY col groups rows and lets you aggregate them (COUNT, SUM, etc.) — more powerful. For pure deduplication of one column they produce the same result. For complex deduplication with aggregation, only GROUP BY works. Performance is similar on modern optimisers.

Data Types & NULL Handling
Basics⌄
📖 Explanation

SQL data types define what values a column can store. Common types: INT/BIGINT (integers), DECIMAL(p,s) (exact fixed-point — use for money), FLOAT/DOUBLE (approximate — never use for money), VARCHAR(n) (variable-length string up to n chars), DATE (date only), TIMESTAMP (date + time), BOOLEAN.

NULL represents an unknown or missing value — it is not zero, not an empty string, and not false. NULL does not equal anything, including itself: NULL = NULL is NULL (not TRUE). Use IS NULL and IS NOT NULL to check. NULL propagates: any arithmetic or comparison involving NULL returns NULL. Use COALESCE() to provide a default value when NULL is encountered.

DECIMAL(p,s) — exact numeric; use for money; FLOAT is approximate (rounding errors)
VARCHAR(n) — variable-length string; CHAR(n) is fixed-width (pads with spaces)
NULL — unknown value; IS NULL / IS NOT NULL to check; never = NULL
COALESCE(a,b,c) — returns first non-NULL arg; great for defaults
NULLIF(a,b) — returns NULL if a=b; else returns a; prevents divide-by-zero
-- NULL comparison — this NEVER matches! SELECT * FROM employees WHERE manager_id = NULL; -- WRONG SELECT * FROM employees WHERE manager_id IS NULL; -- CORRECT -- COALESCE — substitute default for NULL SELECT name, COALESCE(bonus, 0) AS bonus FROM employees; -- NULLIF — avoid divide-by-zero SELECT total_sales / NULLIF(num_orders, 0) AS avg_order FROM summary; -- CASE with NULL SELECT name, CASE WHEN manager_id IS NULL THEN 'Top-level' ELSE 'Has manager' END AS level FROM employees;
Interview Questions
Q1. Why does WHERE col = NULL never return rows?Reveal
Answer: NULL represents an unknown value. The comparison NULL = NULL evaluates to NULL (not TRUE), because you can't know if two unknown values are equal. SQL's WHERE clause only keeps rows where the condition evaluates to TRUE. Use IS NULL or IS NOT NULL instead.
Q2. What is the difference between COALESCE and ISNULL/NVL?Reveal
Answer: All substitute a default for NULL, but: COALESCE(a,b,c,...) is ANSI SQL standard — returns the first non-NULL argument from any number of arguments. ISNULL(a,b) is SQL Server-specific (only 2 args). NVL(a,b) is Oracle-specific (only 2 args). Always prefer COALESCE for portability across databases.
Q3. Why should you never use FLOAT for financial calculations?Reveal
Answer: FLOAT/DOUBLE uses binary floating-point representation which cannot exactly represent most decimal fractions. 0.1 + 0.2 in floating point is 0.30000000000000004. For money, use DECIMAL(p,s) which stores exact decimal values. Example: DECIMAL(10,2) stores up to 10 digits with 2 decimal places — exact to the penny.

ORDER BY, LIMIT & OFFSET
Basics⌄
📖 Explanation

ORDER BY sorts the result set by one or more columns, ASC (ascending, default) or DESC (descending). NULL values sort LAST by default in ascending order in most databases (FIRST in Oracle). Multiple columns in ORDER BY sort by the first column, then by the second to break ties.

LIMIT (MySQL/PostgreSQL) and TOP (SQL Server) restrict the number of rows returned. OFFSET skips the first N rows — used together with LIMIT for pagination. Warning: without ORDER BY, pagination is non-deterministic — always include ORDER BY when paginating. For large tables, OFFSET pagination is slow — keyset (cursor) pagination is faster.

ORDER BY col ASC/DESC — multi-column sort; NULLs sort last (ASC)
LIMIT n — MySQL/PG; TOP n in SQL Server; ROWNUM in Oracle
LIMIT n OFFSET m — skip m rows, return n; used for pagination
NULLS FIRST / NULLS LAST — PostgreSQL explicit NULL sort order
-- Sort by salary descending SELECT name, salary FROM employees ORDER BY salary DESC; -- Multi-column sort SELECT name, dept_id, salary FROM employees ORDER BY dept_id ASC, salary DESC; -- Top 5 earners SELECT name, salary FROM employees ORDER BY salary DESC LIMIT 5; -- Pagination: page 3 (rows 21-30) SELECT * FROM employees ORDER BY emp_id LIMIT 10 OFFSET 20; -- SQL Server syntax SELECT TOP 5 name, salary FROM employees ORDER BY salary DESC;
Interview Questions
Q1. Why must ORDER BY always be included when using LIMIT/OFFSET for pagination?Reveal
Answer: Without ORDER BY, the database returns rows in an undefined order — it can change between queries (due to query plan variations, parallel execution, or table changes). Pagination without ORDER BY may return the same row twice or skip rows across pages. Always order by a unique column (or combination) like id or created_at + id.
Q2. What is the performance problem with large OFFSET values?Reveal
Answer: With LIMIT 10 OFFSET 10000, the database must scan and discard 10,000 rows before returning 10. This gets slower as OFFSET grows — O(offset) work. Solution: Keyset pagination (cursor-based): WHERE id > last_seen_id LIMIT 10. This is O(1) regardless of how deep you paginate, because it uses an index seek instead of a full scan.
Q3. How do you get the Nth highest salary in SQL?Reveal
Answer: Using OFFSET: SELECT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET N-1. Using subquery: SELECT MIN(salary) FROM (SELECT salary FROM employees ORDER BY salary DESC LIMIT N) t. Modern approach: SELECT salary FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees) t WHERE rnk = N — handles ties correctly.

INSERT, UPDATE & DELETE
Basics⌄
📖 Explanation

INSERT INTO adds rows to a table. You can insert a single row with VALUES, or insert results from a SELECT. UPDATE modifies existing rows — always include a WHERE clause or you'll update every single row. DELETE removes rows matching a WHERE condition — again, without WHERE it deletes all rows. TRUNCATE removes all rows faster than DELETE but cannot be rolled back (DDL) and doesn't fire triggers.

The most important production rule: always run a SELECT with the same WHERE clause before UPDATE or DELETE to preview which rows will be affected. Wrap in a transaction so you can ROLLBACK if needed.

INSERT INTO t (cols) VALUES (...) — single row; or INSERT INTO ... SELECT for bulk
UPDATE t SET col=val WHERE condition — ALWAYS use WHERE; omitting updates ALL rows
DELETE FROM t WHERE condition — ALWAYS use WHERE; omitting deletes ALL rows
TRUNCATE TABLE t — deletes all rows fast; DDL; cannot ROLLBACK; no triggers
-- INSERT single row INSERT INTO employees (name, dept_id, salary) VALUES ('Bob', 20, 85000); -- INSERT from SELECT INSERT INTO archive_employees SELECT * FROM employees WHERE hire_date < '2020-01-01'; -- UPDATE — always WHERE! UPDATE employees SET salary = salary * 1.10 -- 10% raise WHERE dept_id = 10; -- DELETE — always WHERE! DELETE FROM employees WHERE hire_date < '2015-01-01'; -- Safe pattern: preview before delete BEGIN; DELETE FROM employees WHERE emp_id = 99; SELECT ROW_COUNT(); -- confirm count ROLLBACK; -- or COMMIT
Interview Questions
Q1. What is the difference between DELETE, TRUNCATE, and DROP?Reveal
Answer:
  • DELETE: DML; removes specific rows (with WHERE) or all rows; can be rolled back; fires triggers; slow on large tables (row-by-row).
  • TRUNCATE: DDL; removes all rows instantly; resets auto-increment; cannot be rolled back; no triggers.
  • DROP: DDL; removes the entire table structure + data permanently.
Use DELETE for targeted row removal, TRUNCATE for clearing a table, DROP for removing a table entirely.
Q2. What happens if you run UPDATE without a WHERE clause?Reveal
Answer: Every row in the table is updated. This is a very common production incident. Prevention: (1) always preview with a SELECT using the same WHERE first; (2) wrap in a BEGIN transaction and verify ROW_COUNT() before committing; (3) use SET SQL_SAFE_UPDATES=1 in MySQL which prevents UPDATE/DELETE without a WHERE on a key column.
Q3. How do you insert multiple rows efficiently in SQL?Reveal
Answer: Use multi-row VALUES: INSERT INTO t (a,b) VALUES (1,'x'), (2,'y'), (3,'z'). This is far faster than three separate INSERT statements because it requires only one network round-trip, one transaction, and one index update. For bulk loads from files use database-specific tools: COPY in PostgreSQL, LOAD DATA INFILE in MySQL — 10–100x faster than row-by-row inserts.

WHERE Clause & Comparison Operators
Filtering⌄
📖 Explanation

The WHERE clause filters rows before any aggregation. It supports comparison operators (=, != or <>, <, >, <=, >=), logical operators (AND, OR, NOT), and special operators. Operator precedence: NOT first, then AND, then OR. Use parentheses to make complex conditions explicit and avoid precedence bugs.

BETWEEN a AND b is inclusive on both ends. IN (list) is a cleaner alternative to multiple OR conditions. LIKE supports pattern matching: % matches any sequence of characters, _ matches exactly one character.

= <> < > <= >= — comparison operators; use <> not != for portability
BETWEEN a AND b — inclusive on both ends; equivalent to a <= col <= b
IN (v1,v2,...) — match any value in list; cleaner than multiple ORs
LIKE '%pattern%' — % = any chars; _ = exactly one char; case-insensitive in MySQL
NOT — negates condition; NOT IN, NOT LIKE, NOT BETWEEN, NOT NULL
-- Comparison operators SELECT * FROM employees WHERE salary >= 50000; SELECT * FROM employees WHERE dept_id <> 10; -- BETWEEN (inclusive) SELECT * FROM employees WHERE salary BETWEEN 40000 AND 80000; -- IN — replaces multiple ORs SELECT * FROM employees WHERE dept_id IN (10, 20, 30); -- LIKE pattern matching SELECT * FROM employees WHERE name LIKE 'A%'; -- starts with A SELECT * FROM employees WHERE name LIKE '%son'; -- ends with son SELECT * FROM employees WHERE name LIKE '_o%'; -- 2nd char is o -- Precedence — use parentheses! WHERE (dept_id = 10 OR dept_id = 20) AND salary > 60000
Interview Questions
Q1. What is the difference between IN and = ANY in SQL?Reveal
Answer: They are equivalent for simple value lists: WHERE id IN (1,2,3) is the same as WHERE id = ANY(ARRAY[1,2,3]) in PostgreSQL. However, IN with a subquery: WHERE id IN (SELECT id FROM t) vs WHERE id = ANY(SELECT id FROM t) behave identically for non-NULL values. Difference: != ALL(subquery) is equivalent to NOT IN (subquery) — but NOT IN fails silently if the subquery returns any NULL.
Q2. Why does NOT IN fail silently when the subquery returns NULL?Reveal
Answer: WHERE id NOT IN (SELECT dept_id FROM departments) — if any dept_id is NULL, then id NOT IN (...NULL...) evaluates to NULL (not TRUE or FALSE), causing NO rows to be returned at all. Fix: use NOT EXISTS or WHERE dept_id IS NOT NULL in the subquery. This is one of the most common SQL bugs in production.
Q3. What is the performance difference between LIKE '%prefix%' and LIKE 'prefix%'?Reveal
Answer: LIKE 'prefix%' (leading pattern) can use a B-tree index — the database seeks to the first matching value and scans forward. LIKE '%prefix%' or LIKE '%suffix' (leading wildcard) cannot use a standard index — requires a full table scan. For full-text search, use FULLTEXT index (MySQL) or tsvector/GIN index (PostgreSQL).

CASE Expression & Conditional Logic
Filtering⌄
📖 Explanation

The CASE expression is SQL's if/else. It comes in two forms: simple CASE compares one expression against multiple values; searched CASE evaluates independent boolean conditions for each branch. CASE can be used anywhere an expression is allowed: SELECT, WHERE, ORDER BY, GROUP BY, even inside aggregate functions.

A common pattern is using CASE inside SUM or COUNT to create conditional aggregation — count or sum only rows matching a condition, effectively pivoting data horizontally.

Searched CASE WHEN cond THEN val ... ELSE val END — evaluates conditions top-to-bottom
Simple CASE expr WHEN val THEN ... — compares one expression to values
CASE in SELECT — create derived columns based on conditions
SUM(CASE WHEN...) — conditional aggregation; pivot data
CASE in ORDER BY — custom sort order (e.g. 'High' before 'Medium')
-- Searched CASE (most common) SELECT name, salary, CASE WHEN salary >= 90000 THEN 'Senior' WHEN salary >= 60000 THEN 'Mid' ELSE 'Junior' END AS level FROM employees; -- Conditional aggregation (pivot) SELECT dept_id, COUNT(*) AS total, SUM(CASE WHEN salary > 70000 THEN 1 ELSE 0 END) AS senior_count, AVG(CASE WHEN gender = 'F' THEN salary END) AS avg_female_salary FROM employees GROUP BY dept_id; -- CASE in ORDER BY for custom sort ORDER BY CASE priority WHEN 'High' THEN 1 WHEN 'Med' THEN 2 ELSE 3 END
Interview Questions
Q1. What is the difference between searched and simple CASE?Reveal
Answer: Simple CASE: CASE expr WHEN v1 THEN r1 WHEN v2 THEN r2 END — compares one expression to multiple values using equality only. Searched CASE: CASE WHEN cond1 THEN r1 WHEN cond2 THEN r2 END — each WHEN evaluates an independent boolean condition (can use >, LIKE, IS NULL, etc.). Use searched CASE for range conditions; simple CASE for equality matching a single variable.
Q2. How do you pivot rows to columns using SQL?Reveal
Answer: Use conditional aggregation: SELECT dept_id, SUM(CASE WHEN month='Jan' THEN sales END) AS jan, SUM(CASE WHEN month='Feb' THEN sales END) AS feb FROM monthly_sales GROUP BY dept_id. This turns one row per (dept, month) into one row per dept with month values as columns. PostgreSQL also has a CROSSTAB function; SQL Server has a PIVOT keyword.
Q3. What does CASE return when no WHEN matches and there's no ELSE?Reveal
Answer: It returns NULL. This is a common bug — forgetting ELSE means unmatched rows silently produce NULL. Always include an ELSE clause unless NULL is explicitly the desired behaviour for unmatched rows.

String Functions
Filtering⌄
📖 Explanation

SQL provides rich built-in string functions for text cleaning and manipulation. Most functions are consistent across databases, with minor naming differences. Key functions: CONCAT joins strings, UPPER/LOWER changes case, TRIM/LTRIM/RTRIM removes whitespace, LENGTH/LEN counts characters, SUBSTRING extracts a portion, REPLACE substitutes text, LIKE/REGEXP for pattern matching, POSITION/INSTR finds a substring's location.

CONCAT(a,b) or a || b — join strings; CONCAT_WS(sep,...) adds separator
UPPER/LOWER — change case; INITCAP capitalizes first letter (PG/Oracle)
TRIM/LTRIM/RTRIM — remove leading/trailing spaces
SUBSTRING(s, start, len) — extract part of string; 1-indexed
REPLACE(s, old, new) — substitute all occurrences
LENGTH(s) — char count; MySQL: CHAR_LENGTH vs LENGTH (bytes)
-- CONCAT — join strings SELECT CONCAT(first_name, ' ', last_name) AS full_name FROM employees; SELECT first_name || ' ' || last_name AS full_name FROM employees; -- PG/Oracle -- CONCAT_WS (with separator — skips NULLs!) SELECT CONCAT_WS(', ', city, state, country) AS address FROM contacts; -- Cleaning & extraction SELECT UPPER(name) AS upper_name, TRIM(' hello ') AS trimmed, -- 'hello' LENGTH('hello') AS len, -- 5 SUBSTRING(name, 1, 3) AS prefix, REPLACE(phone, '-', '') AS clean_phone, POSITION('@' IN email) AS at_pos, LEFT(email, POSITION('@' IN email)-1) AS username FROM users;
Interview Questions
Q1. How do you extract the domain from an email column in SQL?Reveal
Answer: SUBSTRING(email, POSITION('@' IN email) + 1) — finds the position of '@' then takes everything after it. Or: SPLIT_PART(email, '@', 2) in PostgreSQL. For just the domain name (without TLD): combine with another POSITION call on the '.'. Always test with NULL emails using COALESCE.
Q2. What is the difference between CHAR_LENGTH and LENGTH in MySQL?Reveal
Answer: In MySQL, LENGTH() returns the byte count (for UTF-8, emoji or non-ASCII chars take 2–4 bytes each). CHAR_LENGTH() returns the character count (number of characters, regardless of encoding). For ASCII-only text they're identical. For international text or emoji, use CHAR_LENGTH(). In PostgreSQL, LENGTH() returns character count by default.
Q3. Why does CONCAT_WS skip NULLs but CONCAT doesn't?Reveal
Answer: CONCAT('a', NULL, 'b') returns NULL in standard SQL (NULL propagates). CONCAT_WS(', ', 'a', NULL, 'b') returns 'a, b' — it automatically ignores NULL arguments. This makes CONCAT_WS ideal for building address or name strings where some components may be absent. In MySQL, CONCAT returns NULL if any argument is NULL; in PostgreSQL it treats NULL as empty string.

Date & Time Functions
Filtering⌄
📖 Explanation

Date/time functions are critical for business analytics. Key operations: extracting components (year, month, day), calculating differences between dates, formatting dates for output, and filtering by date ranges. Syntax varies more across databases than most SQL, but the concepts are identical.

Key functions: NOW()/CURRENT_TIMESTAMP returns current datetime, CURDATE()/CURRENT_DATE returns today, DATEDIFF/AGE calculates the difference between dates, DATE_ADD/DATEADD adds an interval, EXTRACT/YEAR/MONTH/DAY pulls out components, and DATE_FORMAT/TO_CHAR formats dates as strings.

NOW()/CURRENT_TIMESTAMP — current datetime; CURRENT_DATE for date only
DATEDIFF(end, start) — MySQL; AGE(end,start) in PG; DATEDIFF(unit,start,end) in SQL Server
EXTRACT(YEAR FROM date) — ANSI standard; YEAR(date) in MySQL
DATE_ADD(date, INTERVAL n unit) — MySQL; date + INTERVAL '1 month' in PG
DATE_FORMAT(date, fmt) — MySQL; TO_CHAR(date,'YYYY-MM-DD') in PG/Oracle
-- Current date/time SELECT NOW(), CURRENT_DATE, CURRENT_TIME; -- Extract components SELECT EXTRACT(YEAR FROM hire_date) AS hire_year, EXTRACT(MONTH FROM hire_date) AS hire_month, EXTRACT(DOW FROM hire_date) AS day_of_week -- PG FROM employees; -- Date difference (days) SELECT name, DATEDIFF(NOW(), hire_date) AS days_employed -- MySQL FROM employees; -- Add / subtract intervals SELECT hire_date, DATE_ADD(hire_date, INTERVAL 1 YEAR) AS review_date FROM employees; -- Filter current month's records SELECT * FROM orders WHERE EXTRACT(YEAR FROM order_date) = EXTRACT(YEAR FROM NOW()) AND EXTRACT(MONTH FROM order_date) = EXTRACT(MONTH FROM NOW());
Interview Questions
Q1. How do you filter rows from the last 30 days?Reveal
Answer: WHERE order_date >= NOW() - INTERVAL '30 days' (PostgreSQL) or WHERE order_date >= DATE_SUB(NOW(), INTERVAL 30 DAY) (MySQL). Avoid WHERE YEAR(order_date) = 2024 style filters on indexed columns — applying a function to the column prevents index use. Always put the arithmetic on the right side (the constant), keeping the column bare for index efficiency.
Q2. What is the problem with using EXTRACT(YEAR...) in a WHERE clause for range filtering?Reveal
Answer: Wrapping a column in a function like EXTRACT(YEAR FROM order_date) = 2024 makes the query non-sargable — the database can't use a B-tree index on order_date because it must compute EXTRACT() for every row. Better: WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01' — this is sargable and can use a range scan on the index.
Q3. How do you calculate a person's age from their birthdate?Reveal
Answer: PostgreSQL: DATE_PART('year', AGE(birth_date)). MySQL: TIMESTAMPDIFF(YEAR, birth_date, CURDATE()). SQL Server: DATEDIFF(YEAR, birth_date, GETDATE()). Note: simply doing YEAR(NOW()) - YEAR(birth_date) gives wrong results for people who haven't had their birthday yet this year — use the database-specific AGE or TIMESTAMPDIFF functions which account for this.

Numeric & Math Functions
Filtering⌄
📖 Explanation

SQL provides comprehensive math functions for calculations. ROUND(n, decimals) rounds to a specified number of decimal places. CEIL/CEILING rounds up, FLOOR rounds down. ABS gives the absolute value. MOD(a,b) or a % b gives the remainder. POWER(n,exp) and SQRT(n) for exponents. For statistical analysis: STDDEV and VARIANCE aggregate functions. These work in SELECT, WHERE, and as part of aggregations.

ROUND(n, d) — rounds to d decimal places; ROUND(n) rounds to integer
CEIL(n) / FLOOR(n) — always round up / always round down
ABS(n) — absolute value; useful for differences and deviations
MOD(a,b) or a%b — remainder; MOD(id,2)=0 filters even rows
POWER(n,e) / SQRT(n) — exponentiation and square root
-- Rounding SELECT ROUND(3.14159, 2) -- 3.14, CEIL(3.1) -- 4, FLOOR(3.9) -- 3, ABS(-42) -- 42, MOD(10, 3) -- 1, POWER(2, 10) -- 1024, SQRT(144) -- 12; -- Financial calculation SELECT order_id, quantity * unit_price AS subtotal, ROUND(quantity * unit_price * 0.18, 2) AS tax, ROUND(quantity * unit_price * 1.18, 2) AS total FROM order_items; -- Filter odd/even IDs SELECT * FROM employees WHERE MOD(emp_id, 2) = 0; -- even
Interview Questions
Q1. What is the difference between ROUND, TRUNCATE, and FLOOR?Reveal
Answer: ROUND(3.5) → 4 (rounds to nearest, ties up). TRUNCATE(3.9, 0) → 3 (removes decimal part without rounding). FLOOR(3.9) → 3 (always rounds down to nearest integer). For negative numbers: FLOOR(-3.1) → -4 (rounds away from zero), TRUNCATE(-3.9) → -3 (truncates toward zero). Use TRUNCATE for financial floor calculations; ROUND for display.
Q2. How do you avoid divide-by-zero errors in SQL calculations?Reveal
Answer: Use NULLIF: numerator / NULLIF(denominator, 0) — if denominator is 0, NULLIF returns NULL, and NULL / anything = NULL (no error). Or CASE: CASE WHEN denominator = 0 THEN NULL ELSE numerator / denominator END. In the result, handle NULL with COALESCE: COALESCE(num/NULLIF(den,0), 0).
Q3. How do you calculate the percentage contribution of each row to a total?Reveal
Answer: Subquery approach: SELECT name, salary, ROUND(salary * 100.0 / (SELECT SUM(salary) FROM employees), 2) AS pct FROM employees. Better with window functions: SELECT name, salary, ROUND(salary * 100.0 / SUM(salary) OVER(), 2) AS pct FROM employees — single pass, no subquery needed.

INNER JOIN & JOIN Types
Joins⌄
📖 Explanation

A JOIN combines rows from two or more tables based on a related column. INNER JOIN (the default) returns only rows where there is a match in both tables — unmatched rows are excluded from both sides. LEFT JOIN returns all rows from the left table and matching rows from the right (NULLs for no match). RIGHT JOIN is the mirror. FULL OUTER JOIN returns all rows from both, NULLs where no match exists. CROSS JOIN produces a Cartesian product — every row from table A combined with every row from table B.

INNER JOIN — only matching rows from both tables
LEFT JOIN — all left rows + matching right; NULLs for unmatched right
RIGHT JOIN — all right rows + matching left; mirror of LEFT JOIN
FULL OUTER JOIN — all rows from both; NULLs where no match
CROSS JOIN — Cartesian product; every combination; A×B rows
-- INNER JOIN: only matched rows SELECT e.name, d.dept_name FROM employees e INNER JOIN departments d ON e.dept_id = d.dept_id; -- LEFT JOIN: all employees, dept may be NULL SELECT e.name, d.dept_name FROM employees e LEFT JOIN departments d ON e.dept_id = d.dept_id; -- Find unmatched rows (employees without a dept) SELECT e.name FROM employees e LEFT JOIN departments d ON e.dept_id = d.dept_id WHERE d.dept_id IS NULL; -- FULL OUTER JOIN SELECT e.name, d.dept_name FROM employees e FULL OUTER JOIN departments d ON e.dept_id = d.dept_id; -- CROSS JOIN (use with care!) SELECT colors.name, sizes.name FROM colors CROSS JOIN sizes;
Interview Questions
Q1. Explain the difference between INNER JOIN and LEFT JOIN with a real example.Reveal
Answer: Say employees has Alice (dept=10), Bob (dept=NULL), and departments has dept 10 (Engineering) and dept 20 (Marketing). INNER JOIN returns only Alice (matched). LEFT JOIN returns Alice (with dept name) AND Bob (with NULL dept name). Use INNER JOIN when you only want complete matches; LEFT JOIN when you want to keep all left rows regardless of match — e.g., 'all employees, show department if they have one'.
Q2. How do you find rows in Table A that don't exist in Table B?Reveal
Answer: LEFT JOIN + IS NULL filter: SELECT a.* FROM a LEFT JOIN b ON a.id = b.id WHERE b.id IS NULL. This is the anti-join pattern — the LEFT JOIN includes all rows from A; filtering WHERE b.id IS NULL keeps only those with no match. Alternative: WHERE a.id NOT IN (SELECT id FROM b WHERE id IS NOT NULL) or WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.id = a.id).
Q3. What causes row multiplication (fan-out) in a JOIN and how do you prevent it?Reveal
Answer: If the join key has duplicate values in either table, each duplicate in table A matches each in table B — a Cartesian product of duplicates. 3 rows with id=5 in A × 2 rows with id=5 in B = 6 output rows. Prevention: (1) ensure the join key is unique in at least one table, (2) use DISTINCT or GROUP BY after joining, (3) verify with COUNT(*) before and after the join.

SELF JOIN & Multi-Table Joins
Joins⌄
📖 Explanation

A SELF JOIN joins a table to itself. It is used for hierarchical data (employees and their managers, who are also employees), finding pairs within the same table, and comparing rows within the same table. You must use aliases to distinguish the two instances of the same table.

Multi-table joins chain multiple joins together. SQL processes them left to right, creating an intermediate result set at each step. You can join as many tables as needed. Table aliases are essential for readability when joining multiple tables.

SELF JOIN — table joined to itself; requires aliases (e AS mgr, e AS emp)
Multi-table JOIN — chain JOINs; SQL processes left to right
Alias clarity — always alias tables; e for employees, d for departments
JOIN on multiple columns — ON a.col1=b.col1 AND a.col2=b.col2
-- SELF JOIN: find each employee's manager SELECT emp.name AS employee, mgr.name AS manager FROM employees emp LEFT JOIN employees mgr ON emp.manager_id = mgr.emp_id; -- SELF JOIN: find pairs with same department SELECT a.name, b.name, a.dept_id FROM employees a JOIN employees b ON a.dept_id = b.dept_id AND a.emp_id < b.emp_id; -- Multi-table JOIN SELECT e.name, d.dept_name, p.project_name, l.city AS office_location FROM employees e JOIN departments d ON e.dept_id = d.dept_id JOIN emp_projects ep ON e.emp_id = ep.emp_id JOIN projects p ON ep.proj_id = p.proj_id JOIN locations l ON d.location_id = l.loc_id;
Interview Questions
Q1. When would you use a SELF JOIN?Reveal
Answer: Three main use cases: (1) Hierarchical data — employee-manager relationships where both are in the same table. (2) Finding pairs — customers who live in the same city, products with the same price. (3) Row comparison — compare consecutive records (previous order date vs current). The key technique: alias the table twice with different names (e1, e2 or emp, mgr).
Q2. Write a query to find all employees who earn more than their manager.Reveal
Answer: SELECT e.name, e.salary, m.name AS manager, m.salary AS manager_salary FROM employees e JOIN employees m ON e.manager_id = m.emp_id WHERE e.salary > m.salary. This is a classic self-join interview question. The key: join employees to themselves using the manager_id → emp_id relationship, then filter where the employee's salary exceeds the manager's.
Q3. Does the order of tables in a JOIN affect the result?Reveal
Answer: For INNER JOIN, no — the result is the same regardless of table order. For LEFT/RIGHT JOIN, yes — order determines which table is 'preserved'. Any LEFT JOIN can be rewritten as a RIGHT JOIN by swapping the tables. Modern query optimisers may reorder INNER JOIN tables for performance, but always produce the correct result. For consistency, put the main/driving table first.

Subqueries & EXISTS
Joins⌄
📖 Explanation

A subquery (inner query) is a query nested inside another query. Subqueries can appear in WHERE, FROM, SELECT, or HAVING clauses. A correlated subquery references the outer query — it is executed once per row of the outer query (can be slow). An uncorrelated subquery runs independently once and its result is reused.

EXISTS tests whether a subquery returns any rows. It stops processing as soon as it finds the first match, making it faster than IN for large datasets. NOT EXISTS is the anti-join pattern. Key insight: prefer EXISTS/NOT EXISTS over IN/NOT IN when dealing with NULLs.

Scalar subquery — returns exactly one value; used in SELECT or WHERE
Inline view / derived table — subquery in FROM clause; must be aliased
Correlated subquery — references outer query; runs once per row; can be slow
EXISTS(subquery) — returns TRUE if any rows; stops at first match
NOT EXISTS — anti-join; safe with NULLs; prefer over NOT IN
-- Scalar subquery in WHERE SELECT name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees); -- Subquery in FROM (derived table) SELECT dept_id, avg_sal FROM (SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id) dept_stats WHERE avg_sal > 70000; -- EXISTS — fast anti/semi-join SELECT name FROM departments d WHERE EXISTS ( SELECT 1 FROM employees e WHERE e.dept_id = d.dept_id ); -- Correlated subquery: salary vs dept avg SELECT name, salary, (SELECT AVG(salary) FROM employees e2 WHERE e2.dept_id = e1.dept_id) AS dept_avg FROM employees e1;
Interview Questions
Q1. What is the difference between a correlated and uncorrelated subquery?Reveal
Answer: Uncorrelated: runs once independently. WHERE salary > (SELECT AVG(salary) FROM employees) — the inner query runs once, its result is reused for every row. Correlated: references the outer query, runs once per outer row. WHERE salary > (SELECT AVG(salary) FROM employees WHERE dept_id = e.dept_id) — runs once per employee. Correlated subqueries can be very slow on large tables; CTEs or window functions are usually faster alternatives.
Q2. When should you use EXISTS instead of IN?Reveal
Answer: Prefer EXISTS when: (1) the subquery could return NULLs (NOT IN with NULLs returns no rows; NOT EXISTS is NULL-safe); (2) the subquery result set is large (EXISTS stops at first match; IN evaluates all values). Prefer IN when: the list is a small, static set of literals. For large correlated subqueries, EXISTS is often faster because it can short-circuit.
Q3. What does SELECT 1 mean inside an EXISTS subquery?Reveal
Answer: It means EXISTS only cares whether any rows are returned — not the actual values. SELECT 1, SELECT *, and SELECT NULL inside EXISTS are equivalent in terms of correctness. The database optimiser ignores the SELECT list inside EXISTS and only checks if the subquery returns at least one row. Using SELECT 1 is a conventional signal to readers that the value doesn't matter.

GROUP BY & Aggregate Functions
Aggregation⌄
📖 Explanation

GROUP BY divides rows into groups and applies aggregate functions to each group. Aggregate functions: COUNT(*) counts all rows (including NULLs), COUNT(col) counts non-NULL values, SUM, AVG, MIN, MAX. A key rule: every column in SELECT must either be in GROUP BY or wrapped in an aggregate function (except in MySQL with ONLY_FULL_GROUP_BY disabled).

HAVING filters groups after aggregation — it is the GROUP BY equivalent of WHERE. WHERE filters individual rows before grouping; HAVING filters groups after. You can reference aggregate results in HAVING.

COUNT(*) — all rows including NULLs; COUNT(col) counts only non-NULLs
SUM / AVG / MIN / MAX — all skip NULLs; always verify expected behaviour
GROUP BY rule — SELECT cols must be in GROUP BY or aggregated
HAVING — filters after aggregation; WHERE filters before; can use aggregates
COUNT(DISTINCT col) — count unique non-NULL values
-- Basic GROUP BY SELECT dept_id, COUNT(*) AS headcount, AVG(salary) AS avg_salary, MAX(salary) AS max_salary FROM employees GROUP BY dept_id; -- HAVING: keep depts with avg salary > 70k SELECT dept_id, AVG(salary) AS avg_sal FROM employees WHERE hire_date > '2018-01-01' -- row filter first GROUP BY dept_id HAVING AVG(salary) > 70000 -- group filter after ORDER BY avg_sal DESC; -- COUNT DISTINCT SELECT COUNT(DISTINCT customer_id) AS unique_customers FROM orders; -- Multi-column GROUP BY SELECT dept_id, EXTRACT(YEAR FROM hire_date) AS hire_year, COUNT(*) AS hires FROM employees GROUP BY dept_id, EXTRACT(YEAR FROM hire_date);
Interview Questions
Q1. What is the difference between WHERE and HAVING?Reveal
Answer: WHERE filters individual rows BEFORE grouping. It cannot reference aggregate functions. HAVING filters groups AFTER aggregation. It can reference aggregate functions like COUNT, AVG, SUM. Rule: use WHERE to reduce rows early (more efficient), use HAVING only when filtering on aggregate results. Example: WHERE salary > 50000 reduces rows before grouping; HAVING AVG(salary) > 50000 keeps only groups whose average exceeds 50000.
Q2. What is the difference between COUNT(*) and COUNT(col)?Reveal
Answer: COUNT(*) counts all rows including those with NULL values in any column. COUNT(col) counts only rows where that specific column is NOT NULL. Example: if 100 rows exist but 'bonus' is NULL for 40 of them, COUNT(*) = 100 and COUNT(bonus) = 60. Use COUNT(*) for total row count; COUNT(col) to count non-missing values; COUNT(DISTINCT col) for unique non-NULL values.
Q3. Can you use a column alias in HAVING?Reveal
Answer: In standard SQL (and PostgreSQL, SQL Server), no — HAVING executes before SELECT, so aliases don't exist yet. You must repeat the expression: HAVING AVG(salary) > 70000. MySQL is an exception — it allows aliases in HAVING. To avoid repetition in any database, use a derived table or CTE: SELECT dept_id, avg_sal FROM (SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id) t WHERE avg_sal > 70000.

UNION, INTERSECT & EXCEPT
Aggregation⌄
📖 Explanation

Set operators combine the results of two queries. UNION combines and removes duplicates; UNION ALL keeps duplicates (faster, use when you know there are no duplicates). INTERSECT returns only rows that appear in BOTH queries. EXCEPT (MINUS in Oracle) returns rows from the first query that don't appear in the second.

Rules for all set operators: (1) both queries must have the same number of columns; (2) corresponding columns must have compatible data types; (3) ORDER BY applies to the final combined result, not individual queries.

UNION — combine + deduplicate; UNION ALL keeps duplicates (much faster)
INTERSECT — rows present in BOTH result sets
EXCEPT / MINUS — rows in first set not in second; Oracle uses MINUS
Rules — same number of columns; compatible types; ORDER BY on final result
-- UNION: combine sales from two regions SELECT customer_id, order_date, amount FROM sales_north UNION ALL -- faster: no deduplication SELECT customer_id, order_date, amount FROM sales_south; -- UNION removes duplicates (use when needed) SELECT email FROM customers UNION SELECT email FROM newsletter_subscribers; -- INTERSECT: customers who also subscribed SELECT email FROM customers INTERSECT SELECT email FROM newsletter_subscribers; -- EXCEPT: subscribers who are NOT customers SELECT email FROM newsletter_subscribers EXCEPT SELECT email FROM customers;
Interview Questions
Q1. When should you use UNION vs UNION ALL?Reveal
Answer: Use UNION ALL by default — it's faster because it doesn't sort/deduplicate. Use UNION only when you genuinely need deduplication across the two result sets. UNION internally does a GROUP BY or sort to find duplicates — significant overhead on large datasets. If you know the two queries can't produce identical rows (e.g., they come from different date ranges), always use UNION ALL.
Q2. What is the difference between EXCEPT and NOT IN / NOT EXISTS?Reveal
Answer: They achieve the same result but differently. EXCEPT compares entire rows (all columns must match). NOT IN / NOT EXISTS compares on specific key columns you specify. Use EXCEPT when comparing all columns; use NOT EXISTS when doing a targeted anti-join on a key. Also: EXCEPT handles NULLs correctly (NULLs are considered equal for comparison purposes in EXCEPT).
Q3. Can you ORDER BY inside individual UNION queries?Reveal
Answer: No. ORDER BY applies to the final combined result, not individual parts. This is correct: (SELECT a FROM t1) UNION (SELECT a FROM t2) ORDER BY a. If you need to label rows and sort by source: SELECT a, 'source1' AS src FROM t1 UNION ALL SELECT a, 'source2' FROM t2 ORDER BY src, a.

ROLLUP, CUBE & GROUPING SETS
Aggregation⌄
📖 Explanation

ROLLUP creates subtotals and grand totals automatically. GROUP BY ROLLUP(a, b) produces three levels: (a,b), (a), and () — the grand total. It follows a hierarchy: right-to-left rollup. CUBE produces all possible combinations of subtotals: GROUP BY CUBE(a, b) produces (a,b), (a), (b), and (). GROUPING SETS gives you explicit control over which groupings to compute. The GROUPING() function returns 1 when a column is part of the aggregate subtotal (NULL due to rollup), helping distinguish real NULLs from rollup NULLs.

ROLLUP(a,b,c) — hierarchical subtotals: (a,b,c),(a,b),(a),() — grand total
CUBE(a,b,c) — all 2^n grouping combinations; expensive for many columns
GROUPING SETS((a),(b),()) — explicit control; most flexible
GROUPING(col) — returns 1 if col is NULL due to ROLLUP/CUBE; 0 if real NULL
-- ROLLUP: totals per year, then grand total SELECT COALESCE(CAST(year AS VARCHAR), 'Grand Total') AS year, COALESCE(product, 'All Products') AS product, SUM(revenue) AS revenue FROM sales GROUP BY ROLLUP(year, product); -- GROUPING() distinguishes real vs rollup NULLs SELECT dept_id, CASE WHEN GROUPING(dept_id)=1 THEN 'ALL DEPTS' ELSE CAST(dept_id AS VARCHAR) END AS dept_label, SUM(salary) AS total_salary FROM employees GROUP BY ROLLUP(dept_id); -- GROUPING SETS: explicit combinations SELECT region, product, SUM(sales) FROM data GROUP BY GROUPING SETS((region, product),(region),(product),());
Interview Questions
Q1. What is the difference between ROLLUP and CUBE?Reveal
Answer: ROLLUP(a,b,c) creates n+1 groupings following a hierarchy from right to left: (a,b,c), (a,b), (a), (). Perfect for time hierarchies (year → quarter → month). CUBE(a,b,c) creates all 2^n possible groupings: (a,b,c), (a,b), (a,c), (b,c), (a), (b), (c), (). Expensive but gives every possible subtotal combination. Use ROLLUP for hierarchical data; CUBE for multidimensional analysis.
Q2. How do you distinguish real NULL values from NULL values generated by ROLLUP?Reveal
Answer: Use the GROUPING(col) function, which returns 1 when the NULL was generated by ROLLUP/CUBE (meaning 'all values'), and 0 when it's a real NULL from the data. CASE WHEN GROUPING(dept_id)=1 THEN 'All Departments' ELSE CAST(dept_id AS VARCHAR) END. Without GROUPING(), you can't tell if dept_id=NULL means 'this employee has no department' or 'this is a total across all departments'.
Q3. What is GROUPING SETS and when would you prefer it over ROLLUP/CUBE?Reveal
Answer: GROUPING SETS lets you specify exactly which grouping combinations you want, without computing all rollup or cube combinations. E.g., GROUP BY GROUPING SETS((region, year), (region), (year)) — subtotals by region+year, by region only, and by year only — but NOT the grand total. More efficient than CUBE when you only need specific combinations; more flexible than ROLLUP when the hierarchy isn't strictly linear.

CTEs (WITH Clause)
Advanced⌄
📖 Explanation

A Common Table Expression (CTE) is a named temporary result set defined with the WITH keyword. CTEs make complex queries readable by breaking them into named, logical steps. Multiple CTEs can be chained together. A Recursive CTE references itself, enabling traversal of hierarchical data like org charts, category trees, or bill of materials — structures that can't be queried with regular JOINs.

CTEs exist only for the duration of the query. They are not materialised by default (the database may or may not re-execute them). For expensive CTEs, some databases support WITH ... AS MATERIALIZED.

WITH cte AS (SELECT...) — named subquery; reusable in the main query
Multiple CTEs — chain with commas; later CTEs can reference earlier ones
Recursive CTE — WITH RECURSIVE; anchor + recursive member; UNION ALL to combine
Readability — CTEs make nested subquery logic linear and understandable
-- Simple CTE WITH dept_stats AS ( SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id ) SELECT e.name, e.salary, d.avg_sal FROM employees e JOIN dept_stats d ON e.dept_id = d.dept_id WHERE e.salary > d.avg_sal; -- Chained CTEs WITH high_earners AS ( SELECT * FROM employees WHERE salary > 80000 ), dept_summary AS ( SELECT dept_id, COUNT(*) AS cnt FROM high_earners GROUP BY dept_id ) SELECT * FROM dept_summary WHERE cnt > 5; -- Recursive CTE: org hierarchy WITH RECURSIVE org_tree AS ( SELECT emp_id, name, manager_id, 0 AS level FROM employees WHERE manager_id IS NULL -- anchor UNION ALL SELECT e.emp_id, e.name, e.manager_id, t.level+1 FROM employees e JOIN org_tree t ON e.manager_id = t.emp_id -- recursive ) SELECT * FROM org_tree ORDER BY level, name;
Interview Questions
Q1. What is the difference between a CTE and a subquery?Reveal
Answer: Both produce a temporary named result set, but: CTEs are defined once at the top of the query and can be referenced multiple times, while subqueries must be repeated if used more than once. CTEs are readable — linear top-to-bottom logic. CTEs can be recursive; subqueries cannot. Performance is similar (both may or may not be materialised). Use CTEs for multi-step logic; subqueries for simple, single-use derivations.
Q2. Explain how a recursive CTE works.Reveal
Answer: A recursive CTE has two parts: (1) Anchor member: the base case query (e.g., top-level rows where manager_id IS NULL). (2) Recursive member: references the CTE itself, adding one level per iteration. They are combined with UNION ALL. The database keeps executing the recursive member until it returns no more rows. A LIMIT or MAX recursion depth prevents infinite loops. Classic uses: org hierarchies, file system trees, path finding.
Q3. Can a CTE reference another CTE defined in the same WITH clause?Reveal
Answer: Yes — later CTEs in the same WITH clause can reference earlier ones. Order matters: WITH a AS (...), b AS (SELECT * FROM a WHERE ...) — b can use a. This is what makes chained CTEs so powerful for multi-step transformations. But an earlier CTE cannot reference a later one — they are evaluated top-to-bottom.

Window Functions — ROW_NUMBER, RANK, DENSE_RANK
Advanced⌄
📖 Explanation

Window functions perform calculations across a set of rows related to the current row, without collapsing them into a single output row (unlike GROUP BY). They use the OVER() clause which defines the window: PARTITION BY divides into groups (like GROUP BY but preserves rows), ORDER BY defines the ordering within each partition.

ROW_NUMBER() assigns a unique sequential integer to each row — no ties. RANK() assigns the same rank to tied rows but leaves gaps (1,2,2,4). DENSE_RANK() assigns the same rank to tied rows with no gaps (1,2,2,3). These are the three most commonly tested SQL interview functions.

OVER(PARTITION BY col ORDER BY col) — defines the window; no PARTITION = whole table
ROW_NUMBER() — unique 1,2,3... regardless of ties; for deduplication
RANK() — ties get same rank; gaps after ties: 1,2,2,4
DENSE_RANK() — ties get same rank; NO gaps: 1,2,2,3
Filter window results — wrap in CTE or subquery; cannot use in WHERE directly
-- Rank employees by salary within each dept SELECT name, dept_id, salary, ROW_NUMBER() OVER(PARTITION BY dept_id ORDER BY salary DESC) AS row_num, RANK() OVER(PARTITION BY dept_id ORDER BY salary DESC) AS rank, DENSE_RANK() OVER(PARTITION BY dept_id ORDER BY salary DESC) AS dense_rank FROM employees; -- Top 3 earners per department (most common interview Q) WITH ranked AS ( SELECT name, dept_id, salary, DENSE_RANK() OVER(PARTITION BY dept_id ORDER BY salary DESC) AS rnk FROM employees ) SELECT * FROM ranked WHERE rnk <= 3; -- Deduplicate: keep most recent row per customer WITH latest AS ( SELECT *, ROW_NUMBER() OVER( PARTITION BY customer_id ORDER BY created_at DESC) AS rn FROM orders ) SELECT * FROM latest WHERE rn = 1;
Interview Questions
Q1. What is the difference between ROW_NUMBER, RANK, and DENSE_RANK?Reveal
Answer: For salary values [90k, 80k, 80k, 70k]:
  • ROW_NUMBER: 1,2,3,4 — always unique, no ties
  • RANK: 1,2,2,4 — tied rows share rank, next rank skips numbers
  • DENSE_RANK: 1,2,2,3 — tied rows share rank, no gaps
Use ROW_NUMBER for deduplication. Use DENSE_RANK for 'top N per group' (ensures all ties at rank N are included). Use RANK for sports-style standings.
Q2. Why can't you filter window function results directly in WHERE?Reveal
Answer: Window functions are evaluated after WHERE and GROUP BY (in the SELECT stage). So WHERE RANK() OVER(...) = 1 is invalid — the window function doesn't exist at WHERE evaluation time. Solution: wrap in a CTE or subquery, then filter in the outer query's WHERE: WITH r AS (SELECT *, RANK() OVER(...) AS rnk FROM t) SELECT * FROM r WHERE rnk = 1.
Q3. How would you write a query to find the top-3 salaries per department?Reveal
Answer: WITH ranked AS (SELECT name, dept_id, salary, DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk FROM employees) SELECT * FROM ranked WHERE rnk <= 3. Use DENSE_RANK (not RANK or ROW_NUMBER) so that if two people tie at rank 3, both are included. ROW_NUMBER would arbitrarily drop one; RANK would include them but skip rank 4.

Window Functions — LAG, LEAD, SUM OVER, AVG OVER
Advanced⌄
📖 Explanation

LAG(col, n) accesses the value from n rows before the current row within the partition. LEAD(col, n) accesses n rows ahead. Both are essential for time-series analysis — comparing current vs previous values, computing growth rates. SUM() OVER() and AVG() OVER() compute running totals and moving averages. The ROWS/RANGE BETWEEN frame clause controls which rows are included in the window — essential for proper running totals and moving windows.

LAG(col, n, default) — value n rows back; default if no prior row
LEAD(col, n, default) — value n rows ahead; default if no next row
SUM() OVER(ORDER BY date) — running total; use ROWS BETWEEN for frame
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — cumulative sum frame
ROWS BETWEEN N PRECEDING AND CURRENT ROW — N-period rolling window
-- LAG: month-over-month revenue comparison SELECT month, revenue, LAG(revenue) OVER(ORDER BY month) AS prev_revenue, revenue - LAG(revenue) OVER(ORDER BY month) AS mom_change, ROUND( (revenue - LAG(revenue) OVER(ORDER BY month)) * 100.0 / NULLIF(LAG(revenue) OVER(ORDER BY month), 0) , 2) AS mom_pct_change FROM monthly_revenue; -- Running total SELECT order_date, amount, SUM(amount) OVER( ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS running_total FROM orders; -- 7-day moving average SELECT date, sales, AVG(sales) OVER( ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW ) AS ma_7 FROM daily_sales;
Interview Questions
Q1. How do you calculate month-over-month percentage growth using LAG?Reveal
Answer: SELECT month, revenue, LAG(revenue) OVER (ORDER BY month) AS prev_rev, ROUND((revenue - LAG(revenue) OVER (ORDER BY month)) * 100.0 / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 2) AS growth_pct FROM monthly_revenue. Key: use NULLIF to avoid divide-by-zero when previous month is 0. For partitioned growth (per product per month), add PARTITION BY product_id.
Q2. What is the difference between ROWS BETWEEN and RANGE BETWEEN in window frames?Reveal
Answer: ROWS BETWEEN: physical rows — counts actual row positions. ROWS BETWEEN 2 PRECEDING AND CURRENT ROW always uses exactly 3 rows. RANGE BETWEEN: logical values — includes all rows with the same ORDER BY value as 'peers'. If two rows have the same date, RANGE includes both as part of the 'current' frame; ROWS treats them as distinct positions. For running totals, ROWS is usually what you want for precision.
Q3. Write a query to find consecutive days with sales above a threshold.Reveal
Answer: Use LAG to detect breaks in sequence: WITH gaps AS (SELECT date, sales, CASE WHEN LAG(date) OVER (ORDER BY date) = date - INTERVAL '1 day' THEN 0 ELSE 1 END AS new_streak FROM sales WHERE sales > threshold), streaks AS (SELECT *, SUM(new_streak) OVER (ORDER BY date) AS streak_id FROM gaps) SELECT streak_id, MIN(date), MAX(date), COUNT(*) AS days FROM streaks GROUP BY streak_id HAVING COUNT(*) >= N.

FIRST_VALUE, LAST_VALUE, NTILE, PERCENT_RANK
Advanced⌄
📖 Explanation

FIRST_VALUE(col) returns the first value in the window frame. LAST_VALUE(col) returns the last — but its default frame is ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, so it only sees up to the current row unless you explicitly extend the frame to ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. NTILE(n) divides rows into n equal buckets and assigns each row a bucket number — useful for quartile/decile analysis. PERCENT_RANK and CUME_DIST give relative position within the partition.

FIRST_VALUE(col) OVER(...) — first value in window; useful for baseline comparisons
LAST_VALUE(col) OVER(... ROWS BETWEEN ... AND UNBOUNDED FOLLOWING) — must extend frame!
NTILE(n) — divide into n equal buckets; bucket 1=top, n=bottom (with ORDER BY DESC)
PERCENT_RANK() — relative rank as 0 to 1; (rank-1)/(rows-1)
CUME_DIST() — cumulative distribution; fraction of rows ≤ current value
-- FIRST_VALUE: compare each sale to dept best SELECT name, dept_id, salary, FIRST_VALUE(salary) OVER( PARTITION BY dept_id ORDER BY salary DESC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING ) AS dept_max_salary FROM employees; -- NTILE(4): split into salary quartiles SELECT name, salary, NTILE(4) OVER(ORDER BY salary DESC) AS quartile FROM employees; -- PERCENT_RANK and CUME_DIST SELECT name, salary, ROUND(PERCENT_RANK() OVER(ORDER BY salary)*100,1) AS pct_rank, ROUND(CUME_DIST() OVER(ORDER BY salary)*100,1) AS cume_dist FROM employees;
Interview Questions
Q1. Why does LAST_VALUE often return unexpected results?Reveal
Answer: LAST_VALUE's default window frame is ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — the window only extends to the current row. So LAST_VALUE just returns the current row's own value! To get the actual last value of the entire partition, you must explicitly set: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. This is one of the most common SQL window function bugs.
Q2. How do you use NTILE to classify customers into high/mid/low value segments?Reveal
Answer: SELECT customer_id, total_spend, NTILE(3) OVER (ORDER BY total_spend DESC) AS segment FROM customer_spending. Bucket 1 = top third (high value), 2 = middle, 3 = bottom. Then: CASE WHEN segment=1 THEN 'High' WHEN segment=2 THEN 'Mid' ELSE 'Low' END AS tier. NTILE handles uneven distributions by putting extra rows in the earlier buckets.
Q3. What is the difference between PERCENT_RANK and CUME_DIST?Reveal
Answer: PERCENT_RANK: (rank - 1) / (total rows - 1). The minimum value is 0 (for the first row). CUME_DIST: number of rows ≤ current value / total rows. The minimum value is > 0. For the top earner: PERCENT_RANK = 0, CUME_DIST = 1/n. Use CUME_DIST for 'what % of employees earn at or below this salary'; use PERCENT_RANK for relative ranking position.

Indexes & Query Performance
Expert⌄
📖 Explanation

An index is a separate data structure (usually a B-tree) that speeds up data retrieval by avoiding full table scans. Without an index, the database reads every row (full scan). With an index, it jumps directly to the matching rows. Indexes come with a cost: extra storage and slower INSERT/UPDATE/DELETE (index must be kept updated). The golden rule: index columns used in WHERE, JOIN ON, and ORDER BY.

Key concepts: composite indexes cover multiple columns; column order matters (leftmost prefix rule). Covering indexes include all columns needed by a query (no table lookup needed). Non-sargable conditions (function on a column in WHERE) prevent index use.

CREATE INDEX idx ON t(col) — B-tree index on one column
Composite index (a,b) — use when filtering on both; column order = leftmost prefix rule
Covering index — include all SELECT columns; no table lookup; fastest possible
Non-sargable — WHERE YEAR(col)=2024 blocks index; use col BETWEEN instead
EXPLAIN / EXPLAIN ANALYZE — view query plan; look for Seq Scan vs Index Scan
-- Create indexes CREATE INDEX idx_emp_dept ON employees (dept_id); CREATE INDEX idx_emp_comp ON employees (dept_id, salary); -- composite CREATE UNIQUE INDEX idx_email ON users (email); -- Covering index (includes all needed cols) CREATE INDEX idx_cover ON orders (customer_id, order_date) INCLUDE (amount); -- PostgreSQL syntax -- EXPLAIN: see query execution plan EXPLAIN ANALYZE SELECT * FROM employees WHERE dept_id = 10; -- Non-sargable (BAD — blocks index) WHERE YEAR(hire_date) = 2023 -- function on column -- Sargable (GOOD — uses index) WHERE hire_date BETWEEN '2023-01-01' AND '2023-12-31'
Interview Questions
Q1. When should you NOT add an index?Reveal
Answer: Indexes hurt when: (1) The table is small (<1000 rows) — a full scan is faster than index overhead. (2) The column has very low cardinality (e.g., a boolean 'is_active' with only 2 values) — the index doesn't narrow down results enough to be useful. (3) The table has very frequent writes (logs, events) — every INSERT/UPDATE/DELETE also updates all indexes. (4) The column is rarely queried. Index read vs write tradeoff.
Q2. Explain the leftmost prefix rule for composite indexes.Reveal
Answer: A composite index on (a, b, c) can be used for queries filtering on: a alone, a+b together, a+b+c together. But NOT b alone, c alone, or b+c without a. The index is ordered by a first, then b within same a, then c — so you can only seek efficiently from the leftmost column. Rule: put the most selective (high cardinality) column first, and the column used in ORDER BY last.
Q3. What does EXPLAIN ANALYZE show and what should you look for?Reveal
Answer: EXPLAIN ANALYZE shows the query execution plan with actual timing. Key things to look for: Seq Scan on large tables → needs an index. Index Scan → index is being used. Nested Loop with large loops → may need a better join strategy. Sort with large row counts → add index to avoid sort. Compare estimated rows vs actual rows — large discrepancy means stale statistics (run ANALYZE/UPDATE STATISTICS).

Transactions & ACID Properties
Expert⌄
📖 Explanation

A transaction is a group of SQL operations that execute as a single unit — either all succeed (COMMIT) or all fail (ROLLBACK). Transactions guarantee ACID properties: Atomicity (all or nothing), Consistency (database moves from valid state to valid state), Isolation (concurrent transactions don't interfere), Durability (committed data persists even after crash).

Isolation levels trade off consistency for concurrency: READ UNCOMMITTED, READ COMMITTED (default in most DBs), REPEATABLE READ, SERIALIZABLE. Higher isolation = fewer concurrency issues but lower throughput.

BEGIN / START TRANSACTION — start; COMMIT to save; ROLLBACK to undo
SAVEPOINT name — partial rollback point within a transaction
ACID — Atomicity, Consistency, Isolation, Durability
Dirty read / Non-repeatable / Phantom read — concurrency anomalies per isolation level
SERIALIZABLE — highest isolation; prevents all anomalies; lowest concurrency
-- Transfer funds: both ops or neither BEGIN; UPDATE accounts SET balance = balance - 500 WHERE account_id = 1; UPDATE accounts SET balance = balance + 500 WHERE account_id = 2; -- Save if both succeeded COMMIT; -- Or undo everything if error occurred ROLLBACK; -- SAVEPOINT: partial rollback BEGIN; INSERT INTO orders ...; SAVEPOINT after_order; INSERT INTO payments ...; -- Payment failed? Roll back to savepoint ROLLBACK TO after_order; COMMIT; -- Set isolation level SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
Interview Questions
Q1. Explain ACID properties with a real-world example.Reveal
Answer: Bank transfer of ₹500 from Account A to B:
  • Atomicity: Either both debit A and credit B happen, or neither. No partial state.
  • Consistency: Total money in the system is the same before and after.
  • Isolation: Another transaction reading Account A during the transfer sees either the old balance or the new balance, not an in-between state.
  • Durability: Once COMMITted, the transfer survives a server crash.
Q2. What are dirty reads, non-repeatable reads, and phantom reads?Reveal
Answer:
  • Dirty read: T1 reads data that T2 has modified but not yet committed. T2 then rolls back — T1 read invalid data.
  • Non-repeatable read: T1 reads a row, T2 updates and commits it, T1 reads the same row again and gets different data.
  • Phantom read: T1 queries a range, T2 inserts a row in that range and commits, T1 re-queries and gets an extra row.
Higher isolation levels prevent more of these anomalies.
Q3. What is the difference between TRUNCATE and DELETE within a transaction?Reveal
Answer: DELETE is DML — it can be rolled back within a transaction. TRUNCATE is DDL in most databases — it auto-commits and cannot be rolled back (in MySQL, SQL Server). In PostgreSQL, TRUNCATE is transactional and CAN be rolled back. This is a critical difference in disaster recovery. Always wrap DELETE in an explicit transaction so you can ROLLBACK if the WHERE clause was wrong.

Views, Stored Procedures & Triggers
Expert⌄
📖 Explanation

A VIEW is a named stored SELECT query. It appears as a virtual table. Views simplify complex queries, enforce security (expose only needed columns), and provide abstraction. A materialized view stores the query results physically and must be refreshed — great for expensive aggregations that don't need real-time data.

Stored Procedures are compiled SQL programs stored in the database, accepting parameters and containing control flow (IF, loops, variables). They reduce network roundtrips for multi-step operations. Triggers automatically execute SQL when a DML event occurs (INSERT, UPDATE, DELETE) — used for audit logging, enforcing business rules, and cascading updates.

CREATE VIEW v AS SELECT... — virtual table; no data stored; always fresh
Materialized View — stores result; fast reads; requires REFRESH
CREATE PROCEDURE name(params) AS... — compiled, reusable SQL program
CREATE TRIGGER name BEFORE/AFTER event ON table — auto-fires on DML
INSTEAD OF trigger — replaces the triggering operation (for updatable views)
-- Simple VIEW CREATE VIEW vw_senior_employees AS SELECT emp_id, name, dept_id, salary FROM employees WHERE salary > 80000; -- Query the view like a table SELECT * FROM vw_senior_employees WHERE dept_id = 10; -- Stored procedure (MySQL syntax) DELIMITER // CREATE PROCEDURE give_raise(dept INT, pct DECIMAL(5,2)) BEGIN UPDATE employees SET salary = salary * (1 + pct/100) WHERE dept_id = dept; END // DELIMITER ; CALL give_raise(10, 10.0); -- Audit trigger (PostgreSQL) CREATE TRIGGER salary_audit AFTER UPDATE OF salary ON employees FOR EACH ROW EXECUTE FUNCTION log_salary_change();
Interview Questions
Q1. What is the difference between a VIEW and a MATERIALIZED VIEW?Reveal
Answer: A VIEW stores only the query definition — it re-executes the query every time you SELECT from it. Always up-to-date but potentially slow for complex queries. A MATERIALIZED VIEW stores the actual query results as a physical table. Fast to read, but must be refreshed manually (REFRESH MATERIALIZED VIEW) or on a schedule when underlying data changes. Use materialized views for expensive aggregations that don't need real-time data (e.g., daily reports).
Q2. What are the advantages of stored procedures over application code SQL?Reveal
Answer: (1) Performance: pre-compiled execution plan; no parse/compile overhead per call. (2) Network reduction: one procedure call instead of multiple round-trips. (3) Security: grant EXECUTE on procedure without granting direct table access. (4) Reusability: business logic in one place, shared by multiple applications. Downside: harder to version control, test, and debug than application code.
Q3. When would you use a trigger and what are the risks?Reveal
Answer: Use triggers for: audit logging (record who changed what, when), enforcing complex business rules that can't be handled by constraints, cascading updates. Risks: (1) Hidden side effects — INSERT seems simple but triggers a chain of operations. (2) Performance — fires on every row; can slow bulk operations drastically. (3) Hard to debug. (4) Cascading triggers (trigger fires another trigger). Best practice: use triggers sparingly; prefer explicit application logic when possible.

Query Optimization & Execution Plans
Expert⌄
📖 Explanation

Query optimization is the skill that separates good SQL developers from great ones. The database query optimiser generates an execution plan — a tree of operations (scans, joins, sorts, aggregations) with estimated costs. Understanding and reading execution plans lets you identify and fix bottlenecks.

Key optimisation techniques: write sargable conditions (no functions on indexed columns in WHERE), use EXISTS instead of IN for large subqueries, avoid SELECT *, push filters as early as possible (reduce row count before expensive joins), use appropriate join types, and keep statistics up to date so the optimiser makes correct decisions.

EXPLAIN / EXPLAIN ANALYZE — read execution plan; Seq Scan = no index
Sargable predicates — bare column in WHERE; no function wrapping
Filter early — filter before joining; fewer rows = faster joins
EXISTS > IN for large subqueries; short-circuits at first match
Avoid OR on indexed cols — use UNION instead for index utilisation
-- Check execution plan EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 100 AND status = 'shipped'; -- BAD: non-sargable WHERE UPPER(last_name) = 'SMITH' -- index ignored -- GOOD: sargable WHERE last_name = 'Smith' -- index used -- BAD: OR on indexed column prevents index WHERE status = 'new' OR status = 'pending' -- GOOD: use IN or UNION WHERE status IN ('new', 'pending') -- single index scan -- Filter early: reduce rows BEFORE join SELECT e.name, d.dept_name FROM (SELECT * FROM employees WHERE dept_id = 10) e JOIN departments d ON e.dept_id = d.dept_id;
Interview Questions
Q1. What makes a WHERE clause non-sargable and how do you fix it?Reveal
Answer: A condition is non-sargable when it wraps the indexed column in a function, preventing index use. Common non-sargable patterns and fixes:
  • YEAR(date)=2024 → date BETWEEN '2024-01-01' AND '2024-12-31'
  • UPPER(name)='SMITH' → store lowercase, name='Smith', or use a functional index
  • salary + 0 > 50000 → salary > 50000
  • CAST(id AS VARCHAR)='100' → id = 100 (fix the data type)
Q2. Why does SELECT * hurt query performance?Reveal
Answer: (1) Fetches columns you don't need — more I/O, more memory, more network. (2) Cannot use covering indexes (the index must include all columns SELECT * requests — impossible for *). (3) Prevents certain optimisations (index-only scans). (4) In applications, schema changes (added/removed columns) break downstream code silently. Always name the specific columns you need.
Q3. What are statistics in a database and why do they matter for optimisation?Reveal
Answer: Statistics are metadata about the distribution of data in each column — cardinality (distinct values), null fraction, most common values, histogram of value distribution. The query optimiser uses statistics to estimate how many rows a condition will return, which determines join order, join algorithm (hash vs nested loop), and index vs sequential scan decisions. Stale statistics (after bulk inserts/deletes) cause the optimiser to choose bad plans. Fix: ANALYZE (PostgreSQL), UPDATE STATISTICS (SQL Server), ANALYZE TABLE (MySQL).

Database Design & Normalization
Expert⌄
📖 Explanation

Normalization is the process of organizing a database to reduce redundancy and dependency. The normal forms (1NF through 5NF) progressively eliminate different types of data anomalies. 1NF: atomic values, no repeating groups. 2NF: no partial dependencies (non-key columns must depend on the whole PK, not just part of it). 3NF: no transitive dependencies (non-key columns must depend only on the PK, not on other non-key columns). BCNF is a stricter version of 3NF.

Denormalization intentionally adds redundancy for read performance — common in analytics (data warehouses). Star schema (fact table + dimension tables) is the standard analytical model.

1NF — atomic values; no repeated columns (phone1, phone2); no arrays in cells
2NF — no partial dependency; every non-key col depends on WHOLE PK
3NF — no transitive dependency; non-key col depends only on PK, not other cols
BCNF — stricter 3NF; every determinant is a candidate key
Star schema — fact table + dimension tables; denormalized for analytics
-- NOT in 1NF: storing CSV in a column -- BAD: skills = 'SQL,Python,R' -- 1NF fix: separate table CREATE TABLE employee_skills ( emp_id INT, skill VARCHAR(50), PRIMARY KEY (emp_id, skill) ); -- NOT in 2NF (composite PK: order_id + product_id) -- BAD: product_name depends only on product_id, not whole PK -- 2NF fix: move product_name to products table -- NOT in 3NF -- BAD: employees has dept_id AND dept_name -- dept_name depends on dept_id (transitive dep) -- 3NF fix: move dept_name to departments table -- Star schema for analytics -- fact_sales(sale_id, date_id, product_id, amount) -- dim_date(date_id, year, month, quarter) -- dim_product(product_id, name, category)
Interview Questions
Q1. Explain 1NF, 2NF, and 3NF in simple terms.Reveal
Answer:
  • 1NF: Each cell must contain one atomic value. No 'phone1, phone2' columns. No comma-separated lists in a cell. Fix: create a separate table for multi-valued attributes.
  • 2NF: For tables with composite PKs (multiple columns), every non-key column must depend on the ENTIRE primary key, not just part of it. Fix: split into separate tables.
  • 3NF: Non-key columns must depend directly on the primary key, not on other non-key columns (transitive dependency). If 'city' determines 'zip_code', and both are in a table with 'customer_id' as PK, that's a 3NF violation — move city+zip to a separate table.
Q2. When would you deliberately denormalize a database?Reveal
Answer: Denormalize for read performance when: (1) The table is read far more than written (analytics, reporting). (2) JOINs are too expensive and can't be fixed with indexes. (3) Building a data warehouse (star schema is intentionally denormalized). Trade-offs of denormalization: faster reads, but update anomalies (same data in multiple places must stay in sync), more storage, more complex writes. Rule: normalize for OLTP (transactional), denormalize for OLAP (analytical).
Q3. What is a star schema and how does it differ from a normalized schema?Reveal
Answer: A star schema has a central fact table (containing measurable events: sales, clicks, transactions) surrounded by dimension tables (descriptive attributes: date, customer, product). Dimensions are denormalized — all attributes of a product are in one row. Advantages: simpler queries (fewer JOINs), faster aggregations, intuitive for BI tools. Normalized schema (snowflake): dimensions are further normalized into sub-tables. More storage-efficient but requires more JOINs.
